01

What it is

The webengine/ folder of this repo is the source of truth for the Zesty instance. A GitHub Action maps every file to its Zesty resource by ZUID (zesty.config.json) and syncs it over the Instance API.

You stop copy-pasting code into the Zesty Manager. Instead you work in git, open a pull request, see a comment spelling out exactly what the merge will change, and promote through branches. The CMS becomes a deploy target — versioned, reviewable, reversible.

02

The promotion flow

Three branches, two gates. Each step is previewable before it acts.

local work branch

Where you build. No automation runs here — but the branch is still live-previewable.

stage save · no publish

Merging a PR here saves changed files to the instance's dev version. Preview, then promote.

production save + publish

Merging here publishes live — but only the resources that actually differ from what's already published.

local──PR──▶ stage──PR──▶ production every arrow gets an impact comment

06

Stage vs production

PR ▶ stage

Save

  • → writes changed files to the instance's dev version
  • → compared against the current dev content
  • → nothing goes live — preview on the stage domain
PR ▶ production

Save + publish

  • → publishes changed files live (+ purges cache)
  • → compared against the current live version
  • → already-live, identical resources are skipped
07

How the hybrid sync works

Git tells us what was touched; the API tells us what actually differs. Only the intersection acts.

01

Candidate diff

A git diff against the pre-push commit lists the files the merge changed.

02

Status-aware compare

Each candidate is fetched from the instance — dev for stage, live for production — and compared to the repo.

03

Act on real diffs

Identical resources are skipped. No needless saves, no blind republishing — and Manager-side drift is caught.

04

Auto-create new files

A file with no ZUID yet is created in the instance and its new ZUID is written back to zesty.config.json.

08

Why teams want this

Review before live

Previews + an impact comment mean no one publishes blind.

Only real changes ship

Idempotent — re-running never republishes identical content.

Full audit trail

Every content change is a commit, diffable and revertible.

Drift detection

Edits made directly in the Manager surface as a diff.

CI and CD, end to end

Because every change is a PR, you get real CI/CD for a website CMS with nothing but GitHub Actions:

CI — tests & checks

Run linters, HTML/CSS validation, link checks, visual diffs or Lighthouse on the PR. Gate the merge on green.

CD — the save/publish sync

Merge is the deploy. Stage saves; production publishes — automatically, scoped to real diffs. Roll back by reverting a commit.

Tests flow naturally into the same pipeline: a check on the PR, a preview URL to eyeball, an impact comment to confirm scope — then a one-merge deploy. Production-grade delivery, built into the website with ease.
